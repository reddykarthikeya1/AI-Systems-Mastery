## Part 2: Answer Key & Explanations

<details>
<summary><b>Click to expand the Answer Key & Detailed Explanations</b></summary>

#### Answer 1:
- **Authentication:** Verifying the identity of a client (e.g. "You are User #42 with valid credentials").
- **Authorization:** Verifying whether an authenticated user has permission to perform a specific action (e.g. "User #42 has admin privileges to delete records").

#### Answer 2:
Because modern GPUs can compute billions of SHA-256 hashes per second. Algorithms like **Bcrypt** and **Argon2** are intentionally compute- and memory-intensive (Key Stretching) to make brute-forcing mathematically infeasible.

#### Answer 3:
A salt is a random string generated per user and appended to the password before hashing. Even if two users have the password `Password123`, their salted hashes will be completely unique, invalidating precomputed rainbow tables.

#### Answer 4:
1. **Header:** Encodes algorithm and token type.
2. **Payload:** Encodes user claims (`sub`, `role`, `exp`).
3. **Signature:** Cryptographic hash verifying payload integrity and authenticity.

#### Answer 5:
- `HS256`: Both signer and verifier share the exact same private secret key.
- `RS256`: Auth server signs with a **Private Key**; microservices verify using a **Public Key** without ever knowing the private key.

#### Answer 6:
The **`exp`** claim (UNIX timestamp). When expired, `jwt.decode()` raises `jwt.ExpiredSignatureError` and rejects the request.

#### Answer 7:
Standard `==` returns `False` immediately upon the first mismatched character. `secrets.compare_digest()` always takes the exact same number of CPU cycles regardless of match position, preventing timing attacks.

#### Answer 8:
Because the JWT contains all necessary user information in its payload, and the signature proves it was generated by the trusted auth server without tampering.

#### Answer 9:
Access tokens expire quickly (e.g. 15 mins) to minimize damage if intercepted. Refresh tokens securely rotate access tokens without forcing the user to log in again.

#### Answer 10:
Browsers block web apps from fetching data from external domains unless the API server explicitly sends `Access-Control-Allow-Origin` headers.

### Challenge 1: Constant-Time API Key Verifier

**Goal:** Implement a secure API key verification function that is immune to timing attacks.

<details>
<summary><b>Solution Code</b></summary>

```python
import secrets

VALID_API_KEY = "live_secret_key_8492048204"

def authenticate_api_key(client_provided_key: str) -> bool:
    if not client_provided_key:
        return False
    return secrets.compare_digest(client_provided_key, VALID_API_KEY)

# Verification:
print("Correct key check:", authenticate_api_key("live_secret_key_8492048204"))
print("Wrong key check  :", authenticate_api_key("wrong_key_123"))
```

### D1. JWT signature not verified

```python
import jwt

def read_token(token: str) -> dict:
    return jwt.decode(token, options={"verify_signature": False})
```

**Observed symptom:** Any attacker can mint a token granting themselves any role.

**(a)** What exactly does this code fail to check?

**(b)** What is the correct call?

**(c)** Name two further claims that must be validated even with a valid signature.

<details>
<summary><b>Show the diagnosis</b></summary>

It decodes the payload without verifying the **signature**, so the token's contents are entirely attacker-controlled. A JWT is signed base64, not encrypted — anyone can read *and* forge one if you do not check the signature.

**Correct:**

```python
jwt.decode(token, key=SECRET, algorithms=['HS256'])
```

Passing `algorithms` explicitly is mandatory: omitting it historically allowed the **`alg: none`** attack, and permitting both HS256 and RS256 enables the algorithm-confusion attack where the public key is used as an HMAC secret.

**Also validate:** `exp` (expiry — verified by default, do not disable), and `aud`/`iss` (a token minted for a different service or tenant must be rejected). Add `nbf` if you issue future-dated tokens.

</details>

### D2. Timing attack on token comparison

```python
def check_api_key(supplied: str, expected: str) -> bool:
    return supplied == expected
```

**Observed symptom:** Functionally correct; leaks the key over the network to a patient attacker.

**(a)** How does `==` leak information?

**(b)** What is the correct comparison?

**(c)** Does this apply to bcrypt password checks too?

<details>
<summary><b>Show the diagnosis</b></summary>

String `==` **short-circuits** at the first differing byte. Comparing a wrong key returns marginally faster the earlier the mismatch occurs. Averaged over enough requests, an attacker recovers the key one byte at a time.

**Correct:** `hmac.compare_digest(supplied, expected)`, which is constant-time with respect to content.

**Not needed for bcrypt:** `bcrypt.checkpw` is already constant-time internally, and more importantly the attacker is comparing against a *hash* whose computation dominates any comparison timing. The rule applies to any direct comparison of a **secret you hold in plaintext**: API keys, session tokens, HMAC signatures, CSRF tokens, password-reset tokens.

</details>

### D3. Password hashed with SHA-256

```python
import hashlib

def hash_password(pw: str) -> str:
    return hashlib.sha256(pw.encode()).hexdigest()
```

**Observed symptom:** The database is stolen and 80% of passwords are recovered within a day.

**(a)** Why is SHA-256 the wrong primitive here?

**(b)** What should be used, and what property makes it right?

**(c)** What does a salt protect against, and what does it *not* protect against?

<details>
<summary><b>Show the diagnosis</b></summary>

SHA-256 is designed to be **fast** — billions of hashes per second on a GPU. That is exactly the wrong property for a password hash, where you want each guess to be expensive. There is also no salt here, so identical passwords produce identical hashes.

**Use** bcrypt, scrypt, or Argon2id. Their defining property is a **tunable work factor** — you raise the cost as hardware improves, and the same parameter is stored in the hash so old hashes remain verifiable. Module 16 uses `bcrypt`.

**A salt** prevents precomputation: rainbow tables and the instant cracking of duplicate passwords across accounts. It does **not** slow down an attack on a single password — only the work factor does that. You need both.

</details>

### D4. Authorisation checked in the wrong place

```
@app.get("/documents/{doc_id}")
async def get_document(doc_id: int, user = Depends(current_user)) -> dict:
    doc = await db.get_document(doc_id)
    return doc
```

**Observed symptom:** Any authenticated user can read any document by changing the id in the URL.

**(a)** What is the difference between what this checks and what it needs to check?

**(b)** What is this vulnerability called?

**(c)** Where should the check live so it cannot be forgotten on the next endpoint?

<details>
<summary><b>Show the diagnosis</b></summary>

`Depends(current_user)` proves **authentication** — who you are. It says nothing about **authorisation** — whether *this* user may read *this* document. The ownership check is simply absent.

**Called:** **IDOR** (Insecure Direct Object Reference), or broken object-level authorisation — consistently near the top of the OWASP API Security Top 10.

**Where the check belongs:** in the data-access layer, not the route. Make the query itself scoped — `WHERE id = :doc_id AND owner_id = :user_id` — so an unauthorised row is *unfetchable* rather than fetched-then-checked. A route-level `if doc.owner_id != user.id: raise 403` works but relies on every future endpoint remembering it. Push the constraint down to where forgetting is impossible.

</details>

### D5. Refresh token that never expires

```python
ACCESS_TOKEN_TTL = 15 * 60          # 15 minutes
REFRESH_TOKEN_TTL = None            # never expires
```

**Observed symptom:** A leaked refresh token grants permanent access, and logging out does not revoke it.

**(a)** Why does a short access-token TTL not help here?

**(b)** What two mechanisms make refresh tokens revocable?

**(c)** Why are JWTs a poor choice for the refresh token specifically?

<details>
<summary><b>Show the diagnosis</b></summary>

The access token expiring in 15 minutes is irrelevant when the holder can mint a fresh one forever. The refresh token *is* the long-lived credential, so it needs the strongest handling.

**Two mechanisms:** (1) **server-side storage** — keep refresh tokens in a table or in Redis so logout can delete them and an admin can revoke a session; (2) **rotation with reuse detection** — issue a new refresh token on every use and invalidate the old one; if an old one is ever presented again, that means it was stolen, so revoke the entire token family.

**JWTs are wrong for refresh tokens** because their whole appeal is being stateless and self-validating — which means unrevocable. Use an opaque random token backed by server state. Keep the JWT for the short-lived access token where statelessness is genuinely worth it.

</details>
